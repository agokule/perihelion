# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Perihelion is a C++23 Newtonian gravity simulator of the solar system, rendered with raylib + Dear ImGui (via rlImGui). It targets both native desktop builds and the web (via Emscripten).

## Build commands

The project uses `just` (see `justfile`) as the command runner, wrapping CMake:

- `just build` — configure + build in Debug mode (default). Pass `Release` for a release build: `just build Release`.
- `just build-web` — same, but cross-compiled with `emcmake`/Emscripten for the web target; configures/builds into `build-web/` (a separate directory from the native `build/`, so you can keep both around at once).
- `just clean` — delete both the `build/` and `build-web/` directories.
- `just web-server` — serve `build-web/` over `python -m http.server` (run after `build-web`).
- `just web-open` — open the served web build in a browser.

There is no separate lint step and no test suite in this repo.

CMake uses `FetchContent` to pull raylib 6.0, Dear ImGui, and rlImGui at configure time (see `CMakeLists.txt`); expect the first configure to take a while. raylib is no longer patched at fetch time (`patches/` has been removed) — the one thing that patch existed for, faster camera pan/move speed, is now handled by `src/viewport/camera.cpp`'s own copy of raylib's `UpdateCamera` (see "Input/camera modes" below) instead of forking raylib itself. The project targets C++23 (bumped from C++20). Debug builds additionally pass `-g` (or `/Zi` under MSVC) for debug symbols.

Sources are picked up via `file(GLOB_RECURSE SOURCES "src/*.cpp" "src/*.h")`, so a new `.cpp` file anywhere under `src/` is automatically included in the build — no CMakeLists.txt edits needed. This glob matches `.cpp`/`.h` only; header-only types use `.hpp` and are pulled in transitively via `#include`.

## Architecture

### Entry point and app states

`src/main.cpp` owns the window/camera setup and the main loop. It holds an `AppState` (`src/AppState.hpp`) that the loop switches on each frame; currently only `AppState::Simulation` is implemented (`AppState::PresetSelection` is a stubbed-out TODO case for a future preset-picker screen, not yet built).

All simulation-specific state and behavior (physics stepping, camera-follow, 3D drawing, object selection) lives in `SimulationScreen` (`src/physics/SimulationScreen.hpp`/`.cpp`), which `main.cpp` drives explicitly per frame in this order: `simulate_physics` → `update_camera` → `draw_world` (inside `BeginMode3D`/`EndMode3D`, alongside the `Skybox` draw and the in-progress "adding object" preview and velocity-arrow drawing) → `draw_object_selection_ui`. Object selection is an explicit two-step handshake: `draw_object_selection_ui` returns an `optional<ObjectSelection>` describing what the user picked (via the bottom `ObjectSelector` combo or by clicking a 3D outline), and `main.cpp` is responsible for calling `select_object` with it — this keeps the actual state transition visible in `main` rather than buried in UI-drawing code. `main.cpp` only actually calls `select_object` when neither `adding_object` nor `changing_velocity_of_obj` is active, so a click meant to place an object or drag the velocity arrow can't also reselect a different object underneath it.

`main.cpp` has grown beyond just the loop skeleton: it now also owns the right-click context-menu handshake, the "place a new object" flow, the click-and-drag velocity-arrow editing with optional axis locking (see "Object creation, editing, and velocity dragging" below), a gear-icon button (top-right) that toggles the `SettingsEdit` panel, and dev-only toggles for ImGui's demo/metrics windows (now `P`/`O` — moved off `Z`/`X` so those keys are free to mean world axes during velocity-arrow axis locking). 3D-view input handling (right-click, velocity-arrow dragging) is gated behind an `imgui_wants_io()` lambda (`ImGui::GetIO().WantCaptureKeyboard || WantCaptureMouse`) so it doesn't fire while a widget has focus.

`main.cpp` also owns a `std::optional<SimulationSettings> temp_state` alongside the persistent `settings`, plus a `get_settings_state()` lambda that returns `*temp_state` when set, else `settings` — see "Live-tunable values" below for why this exists and how it's used.

### UI widgets

`src/ui/` holds standalone ImGui widget functions decoupled from `SimulationScreen` (a free function taking plain data in and returning the (possibly updated) selection, with no dependency on `SimulationScreen` internals). Current widgets:

- `ObjectSelectorCombo.hpp`/`.cpp` — just the combo-box part: `int ObjectSelectorCombo(const std::vector<Object>&, int currently_selected)`, sized to the longest name and showing each object's type icon. Factored out of `ObjectSelector` so `ObjectEditor`'s "orbit another object" picker (below) could reuse it.
- `ObjectSelector.hpp`/`.cpp` — the bottom-anchored `ObjectSelectorCombo` + an unselect ("X") button + Previous/Next picker; takes `const std::vector<Object>&` (not just names) for the same icon reason as the combo it wraps.
- `ObjectEditor.hpp`/`.cpp` — a panel for editing the currently-selected `Object`'s name/mass/radius/velocity (via `ImGui::DragScalar`/`DragScalarN`) and color (if it's a solid-color object); returns `true` when the user clicks "Done Editing". Now also takes the object's index and `const std::vector<Object>&` of every object, and offers a "Reverse Velocity" button plus a second `ObjectSelectorCombo` + X/Y/Z `RadioButton` + "Orbit this object" button that computes a circular-orbit velocity (`sqrt(G*other.mass/distance)`, rotated 90° about the chosen axis, plus the target's own velocity) around whichever other object is picked.
- `RightClickMenu.hpp`/`.cpp` — a popup opened at the right-click position offering `RightClickActionSelected::CreateObject`/`EditObject`/`FocusOnObject` (only `CreateObject` is wired up in `main.cpp` so far; the other two are TODO).
- `PlaybackControls.hpp`/`.cpp` — a bottom-centered play/pause/fast-forward/fast-backward bar (now finished/committed, replacing the old `SimulationControls`); fast-forward/backward step `speed` through a fixed array of multipliers (`0.25x`…`2.25x`) rather than halving/doubling `delta_time`.
- `GridTypeEdit.hpp`/`.cpp` — three top-right buttons (each disabled when already active) to switch `GridSettings::type` between `Flat`/`SpacetimeCurved`/`None`.
- `SettingsEdit.hpp`/`.cpp` — a panel (opened via the gear-icon button in `main.cpp`) of `DragFloat`/`DragInt` controls for `objects_scale` and every `GridSettings` tunable (grid line counts, spacing, curvature factor, flat grid Y), each with a `HelpMarker`.
- `HelpMarker.hpp`/`.cpp` — a small `(?)`-style `ImGui::TextDisabled` + tooltip helper, used throughout `SettingsEdit`.

`src/ui/imgui_ui_utils.hpp`/`.cpp` underpins all of the above with two things:
- RAII wrappers for ImGui's paired Begin/End calls — `RAIIWindow`, `RAIIDisabled`, `RAIICombo`, `RAIIStyleVar` — so widget code can't forget the matching `End*`/`Pop*` call.
- A CSS-like positioning system for `ImGui::SetNextWindowPos`/`SetNextWindowSize`: build a `NextWindowPosition` with up to four edge offsets (`top`/`bottom`/`left`/`right`, each an `int` pixel offset, `float` percent-of-display, or `AutoPosition{}`) and pass it to `ImGuiSetNextWindowPos`. Setting one edge on an axis anchors to that edge (like CSS `position: absolute` with one of `top`/`bottom` set); setting both edges stretches the window to fill the gap (calls `SetNextWindowSize` internally, so don't combine with `ImGuiWindowFlags_AlwaysAutoResize` on that axis). Helpers `cent_horiz()`/`cent_vert()` wrap the common "centered" case. See the doc comment on `NextWindowPosition` in `imgui_ui_utils.hpp` for the full rules.

### Icon fonts

`src/FontIcons.hpp` defines `NF_*` macros for individual Nerd Font glyphs (look them up at nerdfonts.com/cheat-sheet), used inline in widget labels (e.g. `NF_MD_WEIGHT_KILOGRAM " Mass:"`). `main.cpp` merges `assets/fonts/nerdfont/SymbolsNerdFont-Regular.ttf` into the default ImGui font at startup via `ImFontConfig::MergeMode`, covering the Unicode Supplementary Private Use Area (glyph range `0xF0000`–`0xF0FFF`). This requires `IMGUI_USE_WCHAR32` (defined in `src/ImConfig.hpp`, ImGui's `imconfig.h` override) since those codepoints are above the 16-bit `ImWchar` range.

### Physics model

Physics code now lives under `src/physics/` (moved from flat `src/`): `Object.hpp`/`.cpp`, `SimulationScreen.hpp`/`.cpp`, `Constants.hpp`, `settings.hpp`, and `unit_conversions.hpp`.

- `Object` (`src/physics/Object.hpp`/`.cpp`) is a celestial body: `ObjectType` (`Planet`/`Star`/`BlackHole`/`Moon`, used for `ObjectSelector`'s icon and via `object_type_to_icon`), mass (kg), radius (light-seconds), position/velocity (`Vector3Double`, light-seconds and light-seconds/s), a trail of previous positions for rendering, and `drawing_info` — a `std::variant<ObjectTextureInfo, Color>` so an object can either be textured (loaded presets) or a flat solid color (e.g. objects created via the right-click menu, which start out `WHITE`).
- `ObjectTextureInfo` owns the raylib `Texture`/`Model` for a textured object and defines its own copy/move constructors/assignment; `load_model()` (re)generates the sphere mesh and (re)loads the texture. This matters because `SimulationScreen::add_object` pushes into `scene.objects` — a reallocation there copies (not moves) existing `Object`s and drops their loaded texture/model, so `add_object` calls `load_model()` on every object afterward to restore them. `scene.objects` reserves capacity for 100 up front (`load_preset`) specifically to make that reallocation rare.
- Distances/positions are stored in **light-seconds** everywhere, including inside the gravity calculation now: `src/physics/Constants.hpp`'s `gravitational_constant` (`2.477e-36`) and `speed_of_light` (`1`) are expressed directly in light-second units, so Newton's law of gravitation is applied without ever converting to/from meters. `src/physics/unit_conversions.hpp` (`convert_light_seconds_to_meters`/`convert_meters_to_light_seconds`) still exists but as of this writing has no callers anywhere in the codebase — it's dead code left over from before this change.
- `src/physics/settings.hpp` holds `GridType`, `GridSettings`, `SimulationSettings`, and `ObjectSelection` (moved out of `SimulationScreen.hpp` so UI widgets like `GridTypeEdit`/`SettingsEdit` can include just the settings types without pulling in all of `SimulationScreen`). See "Live-tunable values" below for `SimulationSettings`'s value-vs-reference change.
- `Vector3Double` (`src/Vector3Double.hpp`/`.cpp`) is a double-precision 3D vector used for physics/position math, distinct from raylib's single-precision `Vector3` used for rendering; `to_vector3()` bridges the two at the render boundary. It now also has a unary `-` operator (used e.g. by `ObjectEditor`'s "Reverse Velocity" button).
- Gravity is simulated with a brute-force O(n²) pairwise integrator, substepped `substeps_per_frame` times per rendered frame (see `SimulationScreen::simulate_physics`), and is a no-op while `SimulationSettings::paused` is set.

### Object creation, editing, and velocity dragging

Right-clicking in the 3D view (when nothing else has ImGui focus) deselects the current object and opens `RightClickMenu` at the click location. Choosing "New Object" builds a template `Object` (white, `ObjectType::Planet`, mass `1e20`, radius `0.005`) and sets up a `temp_state` override (paused, a flat `GREEN` grid at `flat_grid_y = 0`) so placement has a visible reference plane without touching the persisted settings; the object then tracks the mouse along that plane (`ray_y_plane_intersection(ray, temp_state->grid.flat_grid_y)`) every frame until the user presses Enter, which calls `SimulationScreen::add_object` and clears `temp_state`. While placing, holding Up/Down (Left Shift to slow from 6 to 2 units/s) moves `temp_state->grid.flat_grid_y` itself, so an object can be placed off the y=0 plane. This preview-then-confirm object is owned by `main.cpp` as `std::optional<Object> adding_object`, not by `SimulationScreen`. `ObjectEditor` is shown whenever an object is selected, editing it in place by reference.

The selected object's velocity can also be dragged directly in the 3D view. `draw_3d_arrow` (`src/viewport/utils.hpp`/`.cpp`) draws an arrow from the object out to its velocity-derived tip and returns a `Cone` (tip/base points + radius) describing its arrowhead; the tip position itself is `velocity_to_arrow_offset(velocity, surface_radius, velocity_arrow_scale)` (object-relative: out to the object's surface, then further by `velocity * velocity_arrow_scale`), with `arrow_offset_to_velocity` as its inverse — both factored into `viewport/utils` so the same math backs both the drawn arrow and the drag logic below.

Dragging is no longer click-to-grab: pressing `V` while the arrow is on-screen and the cursor is visible (`!camera_pan_enabled`) starts it via `main.cpp`'s `change_velocity_using_cone`, which keeps running every frame (independent of mouse buttons) until a left-click stops it and confirms the new velocity. The first frame of a drag also installs a `temp_state` override with a flat `ORANGE` grid at the arrow tip's current Y, giving a visual reference plane for the drag. Without an axis lock, velocity is re-derived every frame from where the mouse ray hits the y=0 plane, hit-tested against a *local* camera built from `SimulationScreen::camera_offset_from_selected()` rather than the real `Camera3D`, because raylib's `Camera3D` is single-precision and loses too much precision for accurate mouse-ray math once the followed object is far from the world origin — `camera_offset_from_selected()` keeps that offset in `Vector3Double` instead.

While dragging, pressing `X`/`Y`/`Z` locks the drag to that world axis (`get_axis_from_key`/`Axis`/`AxisChangeInfo` in `main.cpp`) and force-pauses via `temp_state`. Locking captures the arrow tip's current object-relative offset (`AxisChangeInfo::original_pos`) plus a `horizontal_speed`/`vertical_speed` pair: a synthetic 1-world-unit step along the axis is projected through `GetWorldToScreen` and its *squared* screen-space length used to derive pixels-per-world-unit, so the axis-locked drag tracks the mouse 1:1 regardless of camera zoom. Each subsequent frame just moves `original_pos` along the axis by `mouse_delta · (horizontal_speed, vertical_speed)`. While locked, a `SKYBLUE` guide line is drawn through the arrow's tip along the locked axis (sized relative to the camera's distance to the tip, rather than a large fixed constant, to avoid float-precision wobble in `DrawLine3D`'s single-precision endpoints).

### Presets

`src/Preset.hpp` defines `Preset` (a name + vector of `Object`s) and a static `presets` vector — currently just `"The Solar System"` with real-ish mass/radius/position/velocity values for the Sun through Neptune plus the Moon. `SimulationScreen::load_preset` swaps in a new `Preset` and calls `load_model()` on each `Object` to (re)load its texture and generate its sphere mesh. `src/Preset.cpp` is currently empty (the preset data is header-only).

### Rendering: skybox and grid

`Skybox` (`src/viewport/Skybox.hpp`/`.cpp`, moved from flat `src/`) renders a single equirectangular panorama (`assets/images/myersalex216-space-2638158.jpg`) sampled by view direction in a fragment shader (`assets/shaders/glsl{100,330}/skybox.{vs,fs}`, GLSL version picked by platform), drawn as a unit cube with backface-culling/depth-write disabled so it stays a static backdrop. `main.cpp` calls `skybox.draw()` first thing inside `BeginMode3D`.

`SimulationScreen::draw_world` no longer draws a flat `DrawGrid`; instead `draw_grid` (renamed from `draw_spacetime_curvature`) now handles all three `GridType`s — `SpacetimeCurved` (a grid warped by Flamm's paraboloid: for each vertex it sums each object's contribution to `y` based on Schwarzschild radius and distance, clamped so the paraboloid stays defined), `Flat` (a plain grid pinned to `GridSettings::flat_grid_y` instead of the curvature calculation), and `None` (draws nothing) — and emits its segments via raylib's low-level `rlBegin(RL_LINES)`/`rlVertex3f`/`rlEnd` instead of one `DrawLine3D` call per segment. Line color comes from `GridSettings::grid_color` (default `WHITE`), which the "adding object"/"dragging velocity" flows above temporarily override via `temp_state` to give a colored reference plane.

The grid follows the camera (floored to grid spacing so it doesn't jitter) and is vertically re-centered each frame around the scene's center of mass; recentering now has hysteresis (only actually shifts `center.y` when the change from the previous frame's shift is `>= 0.2`, tracked via `previous_vertical_shift`) layered on top of the original one-frame-lagged `max_y_val`, to avoid visible jitter beyond what the lag alone fixed.

Tunables live in `GridSettings` (moved to `src/physics/settings.hpp`): `curved_grid_slices`, `flat_grid_slices`, `flat_grid_y`, `spacing_between_slices`, `space_time_curve_factor`, `grid_color`, and the `GridType` enum (`SpacetimeCurved`/`Flat`/`None`) — all three variants are now implemented. They're editable live via the `GridTypeEdit` (type picker) and `SettingsEdit` (numeric tunables) widgets, not just via `adjust.h`.

### Live-tunable values (`adjust.h`) and the `temp_state` pattern

`dependencies/adjust/adjust.h` is a vendored single-header library that lets tunable values be edited while the app is running: it re-parses the declaring source file at its exact line number and pokes the new literal into the live variable, triggered by `adjust_update()` (which `main.cpp` calls while holding `adjust_live` or pressing `R`). Its footprint in `main.cpp` has shrunk to just `ADJUST_CONST_BOOL(adjust_live, false)` — the tunables that used to be `ADJUST_CONST_*` declarations (`delta_time`, `substeps_per_frame`, `selected_sensitivity`, `objects_scale`, `velocity_arrow_scale`, and the now-removed `text`) are gone; they're now plain literals baked into the initial `SimulationSettings` aggregate in `main()`, and are edited at runtime through ImGui widgets instead (`SettingsEdit` for the numeric ones, `PlaybackControls` for `delta_time`/`paused`) rather than through `adjust.h`'s file-reparsing mechanism.

`SimulationSettings` (`src/physics/settings.hpp`) now holds its fields **by value**, not by reference (previous versions of this doc described references — that's no longer accurate). `main.cpp` keeps one persistent `settings` plus `std::optional<SimulationSettings> temp_state`; a `get_settings_state()` lambda returns `*temp_state` when set, else `settings`, and virtually every per-frame settings read in `main.cpp` (`simulate_physics`, `update_camera`, `draw_world`, `objects_scale`, `velocity_arrow_scale`) goes through it. `temp_state` is populated with a copy of `settings` (plus overrides — forced pause, a colored flat grid, etc.) at the start of a transient action (placing an object, dragging velocity) and cleared by the `stop_changing_velocity()`/`stop_adding_object()` lambdas when it ends, so those overrides never leak into the persisted `settings`. When adding a new setting, decide whether it belongs in this by-value struct (most things) versus needing its own `adjust.h` declaration (rare now).

`ADJUST_CONST_*` vs. `ADJUST_VAR_*` only matters for release/production builds (`-DCMAKE_BUILD_TYPE=Release`, i.e. `MODE_PRODUCTION`): `CONST` collapses to a real `const` so the value is fixed in shipped builds, while `VAR` stays a plain mutable variable and remains adjustable/writable even in production. In debug builds both behave identically (a live-editable variable). Use `CONST` for values that should be locked down once tuned; use `VAR` only for something that must stay adjustable (or otherwise mutated at runtime) in a production build too.

A variable declared this way must be long-lived (a local in `main`'s outer scope, a class member, or global) — `adjust.h` stores a pointer to it and writes through that pointer later, so it can't be a short-lived local inside a function called every frame. For that case the header offers `ADJUST_FLOAT(v)`/`ADJUST_INT(v)`/etc., which look up (or create) storage keyed by file+line rather than declaring a variable at all; unused in this codebase currently, but useful for one-off tunables inside a function body.

### Input/camera modes

The camera has two modes driven by `SimulationScreen::current_selected_object`: free-fly (`CAMERA_FREE`) when nothing is selected, and a custom orbit-follow mode (`CAMERA_CUSTOM`, hand-rolled spherical-coordinates orbit with easing-based lerping from `dependencies/reasings`) when an object is selected. Both now go through `update_camera` in `src/viewport/camera.hpp`/`.cpp` — Perihelion's own copy of raylib's `UpdateCamera`, kept in-repo instead of patching raylib at `FetchContent` time (the old `patches/raylib-increase-camera-pan-speed.patch` is gone). Owning the copy directly means camera speed constants (`camera_move_speed`, `camera_rotation_speed`, `camera_pan_speed`, `camera_orbital_speed`, `camera_mouse_move_sensitivity`) live in this file rather than a raylib fork, `CAMERA_CUSTOM` can early-out as a no-op (left fully to `SimulationScreen::update_camera`), and a Left Shift "slow mode" divides every speed constant by 3 while held (gated behind the same `!ImGui::GetIO().WantCaptureKeyboard/WantCaptureMouse` check as other 3D-view input). The camera-follow lerp itself (`SimulationScreen::update_camera`) also changed: it now drives off `std::chrono::steady_clock` instead of a frame counter, and turns toward a newly-selected object by slerping the look direction around the camera (`slerp_direction`, a local helper in `physics/SimulationScreen.cpp`) rather than linearly lerping `camera.target`, so the turn happens at constant angular speed.

Cursor lock state (`DisableCursor`/`EnableCursor`) gates whether mouse movement pans the camera vs. interacts with ImGui; the cursor is also force-locked while placing a new object (`adding_object`), and left unlocked (camera panning suppressed) while dragging the velocity arrow (`changing_velocity_of_obj`).

`K` toggles `settings.paused`, which short-circuits `simulate_physics` (the world stops advancing but stays fully drawn/interactive); `PlaybackControls` exposes the same pause state plus fast-forward/fast-backward (stepping `delta_time` through a fixed array of speed multipliers) as a play/pause bar. `P`/`O` toggle ImGui's demo/metrics windows for development (moved off `Z`/`X`, which are now used as world-axis keys — along with `Y` — for locking a velocity drag to one axis; see "Object creation, editing, and velocity dragging" above). While placing an object, Up/Down (Left Shift to slow) move the placement plane's Y instead of a camera action.
